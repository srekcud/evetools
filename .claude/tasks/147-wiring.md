## 5. Ambiguïtés restantes

- **A1 (bloquant A)** : une clé `coverage` à 0 est « inconnue » selon R7 mais « refusée à la construction » selon les cas limites : l'adaptateur doit-il l'écarter (typeId absent) ou laisser le VO lever une exception ?
- **A2 (bloquant A)** : le phpdoc de `JitaMarketService::getWeightedSellPricesWithFallback` (l.315) garantit `coverage`, donc PHPStan niveau 8 signalera le test de présence de R8 ; faut-il élargir ce phpdoc (`coverage?: float`, fichier hors liste) ou ignorer l'erreur localement ?
- **A3 (bloquant B)** : l'invariance « sans modification » est fausse pour 27 tests à forme exacte ; faut-il confirmer la mise à jour mécanique et la position des clés (`warnings` après `missingData`, `buyCostJitaCoveragePercent` après `buyCostStructure`) ?
- **A4 (bloquant B)** : `missingData` du résultat Buy vs Build agrège les deux côtés de chaque composant, alors que `warnings` ne reprend que `totalProductionCost` (coûts retenus) ; cette asymétrie est-elle voulue ?
- **A5 (bloquant C)** : quelle liste alimente l'avis Buy vs Build (R13), `warnings` du résultat ou l'union des composants avec `buyCostJitaCoveragePercent`, et comment marquer `buildAllCost` / `buyAllCost` (l.669, l.680) sans liste dédiée dans l'API ?
- **A6** : les avertissements n'ont pas de `typeName`, donc l'avis Profit Margins ne peut pas nommer un datacore ou un decryptor partiel, absent de `materials` : faut-il ajouter `typeName` ou afficher le typeId ?
- **A7** : au dédoublonnage (R6), l'entrée garde-t-elle la position de sa première apparition, avec la couverture minimale ?
- **A8** : l'exemple « mode plan et coût marginal » n'est reproductible qu'avec M en réaction (ME 0) : est-ce acceptable pour le test ?
- **A9** : les noms `WeightedPrice` (VO du port), `PartialPrice` et la propriété `Cost::$partialPrices` (champ API `warnings`) sont à confirmer.

## 6. Décisions de Sylvain sur les ambiguïtés (2026-10-28)

A1 : l'adaptateur écarte une couverture ≤ 0 (typeId absent, donc prix inconnu, Q1). A2 : phpdoc de `JitaMarketService::getWeightedSellPricesWithFallback` élargi (`coverage?: float`). A3 : mise à jour mécanique des 27 tests à forme exacte ; `warnings` après `missingData`, `buyCostJitaCoveragePercent` après `buyCostStructure`. A4 : `warnings` ne reprend que les coûts retenus du verdict (asymétrie voulue). A5 : l'avis Buy vs Build se base sur `warnings` du résultat, pas de marqueur sur `buildAllCost`/`buyAllCost`. A6 : pas de `typeName` dans le noyau, le front résout le nom depuis le typeId. A7 : première position, couverture minimale. A8 : exemple plan/marginal avec M en réaction (ME 0). A9 : noms `WeightedPrice`, `PartialPrice`, `Cost::$partialPrices`, champ API `warnings`.
Lots : A noyau, B services et API, C front et i18n, un rouge puis un vert chacun, fusion dans main dans cet ordre.
