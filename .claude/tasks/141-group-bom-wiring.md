## 4. Découpage et ordre de câblage (un lot)

Rouge : (1) `ProductionPlanningTest` avec squelettes `ProductionPlanning` et `ProductionPlanRequest` (`planOf` renvoie `new Plan([], [], [])`) ; (2) squelette du nouveau constructeur de `GroupIndustryProjectService` (`buildBom` écrit la BOM d'un plan vide), pour que les tests échouent sur une assertion et non sur un `TypeError` ; (3) réécriture des harnais et attentes (golden, service, intégration avec le test d'invariance D2). Vert : D1-D3, puis D4-D10, suppression de `flattenTree` et `splitJobsByMaxProductionLimit`, `make deptrac` et PHPStan, puis D11.

## 5. Ambiguïtés restantes

- **A1** : la spec veut une construction de `PlanRequest` « partagée » avec `ProductionCostCalculator`, mais ses plafonds viennent des BPC et son mode plan relit `choiceFor` ; recommandation : ne pas toucher le calculateur dans ce lot, l'équivalence reste prouvée par le test de l'issue.
- **A2 (bloquant)** : le `Plan` ne porte ni unités par run ni blueprint ; recommandation : le service lit le producteur SDE (D7) plutôt qu'un résultat enrichi du cas d'usage.
- **A3** : deux items d'une même réaction à des ME différents donnent deux lignes `final` à 0/0, alors qu'aujourd'hui ils n'en font qu'une ; faut-il lire l'activité avant de regrouper ?
- **A4 (bloquant)** : message converti : celui du planificateur (`Target 11399 has no blueprint nor reaction…`) ou l'ancien `No blueprint or reaction found for product type ID 11399` attendu par l.1047 ?
- **A5** : un `maxProductionLimit` à 0 fait lever `Runs` (`InvalidArgumentException`, 400) avec un message qui ne nomme pas le type, contrairement à R10 ; est-ce acceptable ?
- **A6 (bloquant)** : au plafond 10 de Hail L, 35 000 runs donnent 3 500 lignes de job (7 000 pour l.663) ; faut-il garder ces runs dans les tests réécrits ou les réduire ?
- **A7** : parent d'une ligne de copie ou d'invention : celui du premier job du produit dans `Plan::$jobs`, donc null si le produit est aussi une cible ; aujourd'hui, c'est le premier item parcouru.
- **A8** : les noms `ProductionPlanning` et `ProductionPlanRequest` n'ont pas d'entrée au glossaire et sont à valider.
- **A9** : activité de copie lue par `IndustryActivityRepository::findByTypeIdsAndActivityIds` (nouvelle dépendance, un appel groupé) plutôt que par la requête SQL privée de `IndustryTreeService::hasCopyActivity`, qui serait dupliquée.

## 6. Décisions (2026-10-28)

Tranchées par le thread, techniques, sans changement de produit : A1 : calculateur non touché dans ce lot. A2 : le service lit le producteur SDE (D7). A3 : l'activité est lue avant le regroupement ; une réaction se regroupe à ME 0 / TE 0, ce qui garde une seule ligne `final` comme aujourd'hui. A4 : on garde l'ancien message (`No blueprint or reaction found for product type ID …`) que le test existant attend, converti en `RuntimeException`. A5 : accepté, le `Runs` refuse un plafond à 0 (400) ; message sans typeId à nommer plus tard. A6 : un test garde les runs réels de Hail L (35 000 runs, 3 500 lignes) pour prouver le découpage, les autres réduisent les runs. A7 : parent = premier job du produit dans `Plan::$jobs`. A8 : noms `ProductionPlanning` / `ProductionPlanRequest` retenus, termes ajoutés au glossaire au vert. A9 : activité de copie lue par `IndustryActivityRepository::findByTypeIdsAndActivityIds` (un appel groupé).
Q4 de la spec : pas de régénération, issue existante #253.
